# S02 — Тенантність: членство як документ, ролі, ізоляція компаній

> Статус: дизайн затверджено, спека затверджена власником 2026-10-24, реалізовано в гілці `s02-tenancy`. Частина [дорожньої карти](2026-10-22-finflow-roadmap.md). Залежить від [S01](2026-10-23-s01-session-auth-design.md) і [S01A](2026-10-23-s01a-ui-shell-design.md). Розмір: M.

## Мета

Доступ до даних компанії визначає **документ членства з роллю**, який перевіряють правила Firestore й сервер. Член компанії A не бачить і не змінює дані компанії B; Viewer лише читає, Accountant веде дані, Owner керує ще й банками, підпискою й компанією. Компанії створює тільки сервер (з обмеженням кількості на користувача). Це фундамент для запрошень у S16.

## Вихідний стан (перевірено в коді)

- Членство лежить мапою в документі організації: `organizations/{orgId}.members = { <uid>: { role: 'owner' } }`. Правила (`firestore.rules`) перевіряють `request.auth.uid in org.members` через `isMemberOf`.
- Компанію створює браузер: `createOrganization` (`lib/firebase/firestore.ts`, `addDoc`), його викликають `signUpWithEmail` (`lib/firebase/auth.ts`) і Google-гілка `app/(auth)/register/page.tsx`. Правила дозволяють create, якщо користувач єдиний член-owner.
- Перелік «моїх компаній»: `getUserOrganizations` / `userOrganizationsQuery` (`lib/firebase/queries.ts`, запит по `members.<uid>.role != null`); його використовують `login/page.tsx`, `register/page.tsx`, `useOrg`, `OrgSwitcher`.
- Правила для підколекцій: `accounts`, `categories`, `transactions`, `bankConnections` читає/пише будь-який член; `organizations` update дозволено будь-якому члену, лише поля `name` і `currency`; delete заборонено.
- Сервер: `requireOrgMember(uid, orgId)` у `lib/server/auth.ts` читає `organizations/{orgId}.members` через Admin SDK; використовують `api/enablebanking/{session,accounts,callback}`.
- Тести: `tests/rules/firestore.rules.test.ts` (72 тести разом із `client-sdk.test.ts`).
- Індексів колекційних груп немає (`firestore.indexes.json`).
- У проді ~90 тестових компаній і реальна тестова компанія власника, усі зі старою мапою `members`.

## Рішення

| Питання | Рішення |
|---|---|
| Ролі MVP | Три: **Owner**, **Accountant**, **Viewer** |
| Модель членства | Документ `organizations/{orgId}/members/{uid}`; мапу `members` в організації прибираємо |
| Створення компанії | Лише на сервері: `POST /api/orgs`; правила забороняють клієнту створювати організації й членство |
| Ліміт | 3 компанії, де користувач owner (проти фармінгу тріалів) |
| Старі дані | Одноразовий серверний скрипт створює членство (owner) для всіх наявних компаній, нічого не видаляється |
| Доступ до чужого URL | Екран «Немає доступу до цієї компанії» замість вічного скелетона |
| Інтерфейс за роллю | Viewer без кнопок додавання й редагування; Accountant без «Банки» й «Підписка»; Owner усе |

## Обсяг

### 1. Модель даних

- **Членство:** `organizations/{orgId}/members/{uid}` = `{ uid, role, createdAt, addedBy }`, де `role` один із `owner | accountant | viewer`, `uid` дублює id документа (потрібен для запиту по колекційній групі), `addedBy` для засновника дорівнює його `uid`.
- **Організація:** `{ name, currency, ownerId, plan, trialEndsAt, createdAt }` без `members`. `ownerId` лишається довідковим (його виставляє сервер); правами керує лише членство.
- **Константи ролей** в `lib/shell/permissions.ts` (спільні для клієнта й сервера, без імпортів): `ROLES`, тип `Role`, `can(role, action)`; дії: `data.write` (owner, accountant), `bank.manage` (owner), `company.edit` (owner), `subscription.view` (owner).

### 2. Правила Firestore

- Хелпери: `memberRole(orgId)` = `get(.../organizations/$(orgId)/members/$(request.auth.uid)).data.role` (якщо документа немає, доступу немає); `hasRole(orgId, roles)`.
- **`organizations/{orgId}`:** `get` для будь-якої ролі; `list` заборонено (компанії завантажуємо за id зі списку членств); `create` і `delete` заборонені клієнту; `update` лише owner, лише `name` і `currency` з наявною валідацією типів.
- **`organizations/{orgId}/members/{memberId}`:** `read`, якщо `request.auth.uid == memberId` (свій документ) або роль owner; будь-який запис клієнтом заборонено (пише лише сервер).
- **Колекційна група `members`:** правило `match /{path=**}/members/{memberId}` дозволяє `read`, лише коли `resource.data.uid == request.auth.uid` (запит `collectionGroup('members').where('uid','==',uid)`). В індексах додається `fieldOverrides` для `members.uid` (COLLECTION_GROUP, ASCENDING).
- **Підколекції даних** `accounts`, `categories`, `transactions`: `read` для ролей owner, accountant, viewer; `create/update/delete` для owner і accountant, плюс наявна `orgIdMatchesPath`.
- **`bankConnections`:** `read` і запис лише owner.
- Усе інше (інші підколекції й шляхи) закрито за замовчуванням; `_meta` без змін.

### 3. Сервер

- **`requireOrgRole(uid, orgId, allowed: Role[])`** в `lib/server/auth.ts` (заміна `requireOrgMember`, зберігає перевірку формату `orgId`): читає `organizations/{orgId}/members/{uid}` через Admin SDK; відсутнє членство, невідома роль чи роль поза `allowed` дають 403 `forbidden` (однакова відповідь, щоб не можна було розвідати id). Повертає роль.
- **Виклики:** `api/enablebanking/session`, `accounts` і `callback` вимагають `['owner']`.
- **`POST /api/orgs`** (`app/api/orgs/route.ts`, Node runtime): `requireUser` (сесія й Origin), тіло `{ name, currency }`; назва обрізається, 1–120 символів; `currency` з `['PLN','EUR','USD','UAH']`; зайві поля відхиляються (400). Ліміт: у транзакції Admin SDK рахуємо членства користувача з роллю owner (запит по `collectionGroup('members')` за `uid`, роль фільтрується в коді); якщо їх уже 3, повертається 409 `org_limit_reached`. Транзакція створює документ організації (`plan: 'trial'`, `trialEndsAt` = +14 днів, `createdAt` серверним часом, `ownerId`) і документ членства owner разом. Відповідь 201 `{ orgId }`, `Cache-Control: no-store`. Помилки через `errorResponse`, у лог іде лише код.
- Створення не вимагає підтвердженого email (м'яка перевірка з S01 діє лише на підключення банку).

### 4. Клієнт

- `createOrganization` видаляється з `lib/firebase/firestore.ts`; новий `lib/firebase/orgs-client.ts` (`createOrgViaApi(name, currency)`: POST `/api/orgs` із `credentials: 'same-origin'`, мапінг помилок: `org_limit_reached`, мережа). `signUpWithEmail` і Google-гілка реєстрації викликають його після `establishSession`; якщо створення не вдалось, користувач бачить помилку, а не порожній стан.
- `getUserOrganizations` і `userOrganizationsQuery` замінюються на `getMemberships(uid)` (запит по `collectionGroup('members')` за `uid`, повертає `{ orgId, role }[]`) і `getMyOrganizations(uid)` (членства плюс завантаження кожної організації за id, відсутні пропускаються). Користувачі: `login`, `register`, `useOrg`, `OrgSwitcher`.
- `useShell` отримує `role` (читає свій документ членства `organizations/{orgId}/members/{uid}`, пріоритет над «пам'ятною» компанією) і `can(action)`.
- **Екран «Немає доступу»** (`components/shell/NoAccess.tsx`): `AppShell` показує його замість контенту, коли для компанії з URL у користувача немає членства (читання власного документа членства відмовлено/порожнє). Текст «Немає доступу до цієї компанії», кнопка «До моєї компанії» (перша з `getMyOrganizations`, якщо вона є), кнопка «Вийти». Без вічного скелетона.
- **Інтерфейс за роллю** (зручність, а не захист; захист у правилах):
  - Viewer: не показуємо «Дохід / Витрата / Переказ», «Додати рахунок», меню рядка рахунку, редагування рядка журналу, додавання й видалення категорій; форми компанії й категорій доступні лише для читання.
  - Accountant: усе з даними; у меню налаштувань немає «Банки» і «Підписка»; «Компанія» лише для читання.
  - Owner: усе.
  - Прямий перехід не-власника на `settings/banks` чи `settings/subscription` показує «Недостатньо прав» замість сторінки.

### 5. Міграція

`scripts/migrate-memberships.mjs` (Node, Admin SDK, ключ сервісного акаунта береться з `.secrets/` або `GOOGLE_APPLICATION_CREDENTIALS`, нічого не друкується з вмісту, лише лічильники й id):

- За замовчуванням **dry-run**: перелічує організації зі старою мапою `members` і показує, скільки документів членства буде створено.
- `--apply`: для кожної `members.<uid>.role` створює `organizations/{orgId}/members/{uid}` (`role` зі старої мапи, якщо валідна, інакше `owner` для `ownerId`); ідемпотентно (`set` з тим самим вмістом); вивід перевіряється повторним читанням.
- `--drop-members-map` (окремий крок, лише після перевірки в проді): видаляє поле `members` з організацій (`FieldValue.delete()`).
- Чиста функція `planMemberships(orgDocs)` покрита юніт-тестами (ролі, пропуски, зламані дані).
- **Порядок розгортання:** (1) задеплоїти індекс колекційної групи (`firestore.indexes.json`) і дочекатися READY; (2) `--apply` (старі правила й старий код працюють далі); (3) змерджити PR (деплой застосунку); (4) одразу після READY задеплоїти нові правила. Між кроками 3 і 4 застосунок кілька хвилин недоступний (нові правила й старий код несумісні): виконуємо у зручний для власника момент; (5) перевірка; (6) `--drop-members-map`.

## Тестування

- **Правила** (`tests/rules`): матриця 3 ролі × `accounts`/`categories`/`transactions`/`bankConnections`/`members` × read/create/update/delete; відсутність членства; чужа компанія; перелік власних членств колекційною групою (і відмова для чужого `uid` та для запиту без фільтра); організація: create/delete клієнтом відмовлено, update лише owner і лише `name`/`currency`; невідома підколекція закрита. Існуючі тести переписуються під нову модель (дані фікстур створюють документи членства).
- **Юніт:** `requireOrgRole` (відсутнє членство, чужа роль, невалідний `orgId`, збій Firestore це 500, не 403); `POST /api/orgs` (валідація, зайві поля, ліміт 3 і 4-та відмова, атомарність: збій запису членства не залишає організації, формат відповіді, 401 без сесії, 403 для чужого Origin); `can(role, action)`; `planMemberships`.
- **E2E:** реєстрація створює організацію й членство owner (перевірка через документ членства в емуляторі); перехід на URL чужої компанії дає екран «Немає доступу» й кнопку «До моєї компанії»; користувач із роллю Viewer і Accountant (членство створюється допоміжною функцією емулятора) бачить обмежений інтерфейс, а спроба запису з консолі браузера відхиляється правилами; 4-та компанія через API дає 409; наявні сценарії (смоук, `session-auth`, `app-shell`) лишаються зеленими, оновлюється все, що створює компанію напряму через Firestore (допоміжні `seedDoc`/`seedJournal` пишуть і документ членства).

## Критерії готовності

- Член компанії A отримує PERMISSION_DENIED на читання й запис у компанії B (тести правил у CI).
- Клієнт не може створити організацію чи документ членства, не може змінити роль; Viewer не може писати дані; Accountant не бачить і не змінює банки.
- Правила не посилаються на мапу `members` в організації; у коді немає `createOrganization` і `getUserOrganizations`.
- Старі компанії (включно з реальною тестовою власника) відкриваються після міграції; `--drop-members-map` виконано після перевірки.
- Екран «Немає доступу» замість вічного скелетона; інтерфейс відповідає ролі.
- CI зелений: lint без нових помилок, typecheck, юніт, правила, E2E, збірка; перевірка на проді за списком (вхід, відкриття своєї компанії, URL чужої, створення другої компанії, ліміт).

## Ризики

1. **Ціна `get()` у правилах:** кожна операція з даними додає одне читання документа членства (і ліміт 10 `get` на запит). Для одиночних операцій це нормально; пакети в S05 переїдуть на сервер.
2. **Правило колекційної групи `members`** діє для будь-якої колекції з таким ім'ям: тримаємо назву `members` зарезервованою для членства; це записується в CLAUDE.md.
3. **Вікно недоступності між деплоєм застосунку й правил** (кроки 3 і 4 розгортання): коротке, у зручний момент; відкат лишається можливим, доки не виконано `--drop-members-map`.
4. **Гонка ліміту:** обмежена транзакцією Admin SDK; обхід через кілька акаунтів (багато email) лишається, його закриває білінг у S17.
5. **Інтерфейс за роллю не є захистом:** справжню відмову дають правила; тест із консолі браузера це доводить.
6. **Старий код і нова модель:** будь-яке місце, що читає `organizations.members`, перестане працювати; пошук `members` по коду й тестах входить у критерії готовності.

## Уточнення під час реалізації

- **Правила організації суворіші:** `name` (не порожня після `trim`, до 120 символів) і `currency` (PLN, EUR, USD, UAH) перевіряються в самому правилі, а не лише на сервері.
- **Список членств:** `list` документів `organizations/{orgId}/members` дозволено лише owner (спека казала «read»; свій документ читається через `get`, а список власних членств дає запит колекційної групи).
- **Анонімні сесії:** `POST /api/auth/session` відмовляє (403) сесіям анонімного входу Firebase, бо їхня присутність у системі тенантності не передбачена.
- **Стабільний порядок:** `getMyOrganizations` сортує компанії за `createdAt`, щоб «перша компанія» для кнопки «До моєї компанії» була детермінованою.
- **Перемикання компанії в хуках даних:** `useAccounts` і `useCategories` зберігають дані разом з `orgId` і до першого знімка нової компанії віддають порожній список, тож дані попередньої компанії не показуються навіть на кадр.
- **Міграція:** існуюче членство з іншою роллю не перезаписується (рахується як конфлікт); `--drop-members-map` відмовляє, якщо хоча б одного членства з планових бракує; з `FIRESTORE_EMULATOR_HOST` скрипт працює лише з емулятором і без ключів.
- **Скрипт перевірки правил:** `scripts/verify-firestore-rules.mjs` не потребує наявної компанії: лише негативні перевірки й запит колекційної групи від тимчасового користувача. Позитивні шляхи перевіряються вручну на production.
- **Відкладено (див. PROGRESS.md):** перехідний набір правил для production з реальними користувачами; емуляторний тест гонки ліміту; логування повідомлень помилок Firestore.
